MCIPを唯一の統合入口とし、正本はデータ種別ごとに分離する。6つのData & Analysisは特定製品の下位機能ではなく、6つのDomain Productが共同利用する横断サービスとする。MCAHが利用権限と実行を統制し、重要判断はR0〜R4とHuman-in-the-Loopで管理する。

V3.4からの主な変更点（開発ハーネス旧表記の完全廃止）
  1. 6つのData & Analysisを横断共通サービスとして定義。Domain Productとの関係は1対1ではなく多対多とする。
  2. 「解析エンジン」を「解析実行・ジョブ管理基盤」へ改称。解析の受付、Sandbox実行、状態、再試行、版、入出力ハッシュを管理し、計算本体とは分離する。
  3. 工学計算本体を「工学解析・決定論的ソルバー」として独立。OpenSees／Code_Aster／GIS／水理等を置き、生成AIの文章生成と数値計算を混同しない。
  4. Domain Productごとの主利用・副利用を明示。ArcSphereは6要素すべてを空間統合し、CEOSは業務統合、MCIPは権限・承認・根拠・監査を統制する。
  5. データ流を統一。Domain Product → 解析実行・ジョブ管理 → 認識／工学解析／予測エンジン → データ基盤 → Domain Product、の循環とする。
  6. V3.3の11リポジトリ、最先端AI、スマホ3D、Digital Twin、R0〜R4、二重認可、無承認RSI禁止は維持する。
  7. 開発支援基盤をMirai-AI-Coding-Harnessとして正式化。OpenAI／Anthropic／DeepSeekを利用可能とし、MVP対象に変更。本番建設業務用MCAHとは認証情報・権限・Sandbox・Tool・ログを分離する。

工程・原価・契約を正本として、公開データ、進捗・原価予測、資源配置、多目的最適化を主利用する。

動画・写真・GNSS・IMUを取り込み、認識・3D再構築ジョブを実行し、結果をArcSphere、原本をCDEへ渡す。

MCIP／MCAH｜製品横断の統制

MCIPは案件・権限・承認・根拠・監査、MCAHはSkill選択・Tool実行・状態・評価を担当する。解析データの正本を奪わない。

1.2 標準データフロー

Domain Product → MCAH Tool Gateway → 解析実行・ジョブ管理 → 認識／工学解析／予測エンジン → PostgreSQL・CDE・公開データ → Domain Product → MCIP承認・証跡
  1. Domain Productが案件ID・利用者・Skill・入力データ参照を付けて解析を要求する。
  2. MCAHがR0〜R4、案件権限、機密区分、データ品質、許可Toolを事前判定する。
  3. Job OrchestrationがSandboxで処理し、入力・出力ハッシュ、Tool版、状態、費用、再試行を記録する。
  4. 各エンジンは結果と確信度・適用範囲・元データ位置を返す。決定論的ソルバーは計算条件と版を返す。
  5. 結果は正本責任に従って各製品、CDE、PostgreSQLへ保存し、MCIPに承認記録と証跡を残す。
DEVELOPMENT BOUNDARY ― 開発時ハーネスに本番特権を常時付与しない／本番DBへのAgent直接更新は禁止

2. モデル利用方針と配置の選択

2.1 本番建設業務用MCAHで使うモデルとサービス

項目方針
提供元本番建設業務用MCAHはOpenAIとAnthropicの2社に限定する。ローカルLLMは使わない。DeepSeekは開発支援用Mirai-AI-Coding-Harnessでのみ利用可能とし、MCAHの本番データ・本番権限・本番Toolへ直接接続しない。
利用形態両社のサービス内であれば次のいずれも可とする。
・各社APIの直接利用（組織アカウントで発行したAPIキー）
・各社の法人向けサービス（ChatGPT Enterprise／Claude Enterprise／Claude Team。利用者向け画面）
・同じ提供元のモデルをクラウド事業者経由で使う形（Microsoft Foundry／Azure、Amazon Bedrock、Google Vertex AI など）。採用時に契約とデータ取扱条件を個別に確認する
契約・設定の必須条件入力データを学習に使わない設定、データ保持期間、処理リージョンを確認し、Harness Coreのプロバイダー台帳に記録する
機密区分との対応公開・社内：承認済み接続へ送信可／社外秘：Maskingを通してから送信／極秘：モデルに送信しない（オンプレミス配置でも同じ）
ルーティング表Harness Coreで管理（機密区分・難度・費用 → 提供元・モデル・接続経路）。変更はPRとCODEOWNERSの承認でのみ行う

2.2 配置の選択（オンプレミス／クラウド）

現時点の方針：MVPはオンプレミス配置で構築し、本番はクラウド配置で検討中。MVPの段階から deploy/cloud プロファイルも用意し、同じゴールデンセットで両方の結果が一致することを確認してから移行を判断する。

選べるのはMCIP・MCAH・Model Gateway・PostgreSQLなど実行基盤を置く場所。OpenAI・Anthropicのモデル本体は各社（またはクラウド事業者）の環境で動くため、どちらを選んでもモデルへの入力は社外に送られる。

項目A. オンプレミス配置B. クラウド配置
置き場所社内サーバー（VM・コンテナ）Azure／AWSなどの自社テナント
モデルへの通信FortiGateから許可リストのAPIエンドポイントへのみ外向き通信テナントから各社APIへ（可能ならプライベート接続）
APIキーの保管社内のシークレット管理（Vault等）Azure Key Vault／AWS Secrets Manager
データの所在DB・証跡・索引は社内に残るDB・証跡・索引は自社テナントに置く
向いている場合文書・証跡を社外に置きたくない、社内AD・CDEとの近さを優先現場・支店からの利用、拡張性、別リージョンでのBCPを優先
運用負荷ハードウェア・バックアップ・冗長化を自社で持つ費用管理とテナントの権限設計が必要

切り替えの仕組み

  • 配置は環境ごとの配置プロファイル（deploy/onprem・deploy/cloud）で選ぶ。アプリのコードは共通
  • 接続先・キーの参照先・ネットワーク設定はプロファイル側に置き、ルーティング表とポリシーは共通
  • 同じゴールデンセットを両方の配置で実行し、結果が一致することを確認する

APIキーの管理

  • 組織アカウントで発行し、個人アカウントのキーは使わない
  • 環境（開発・検証・本番）とAgentごとに分け、Gitには置かない（Secret Scanで検知）
  • 提供元側で利用上限・予算アラートを設定し、定期的にキーを更新する
  • キーを持つのはModel Gatewayだけ。Agent・利用者には渡さない

5. MCAH設計方針

5.1 Agentは3つに固定し、専門知識はSkillで足す

固定するAgent

  • Orchestrator：質問理解、計画、Skill選択、承認待ちの管理
  • Construction Intelligence：探索、関係分析、矛盾検出、回答・下書き生成
  • Evidence Verifier：引用の実在・一致・機密区分を決定論的に検査

Skill（手順＋許可ツール＋評価セット）

  • 文書系：日報、写真台帳、議事録、NETIS採否、仕様・図面・数量表の照合
  • 空間系：撮影ガイド、3D再構築、設計対現況差分、進捗・出来形候補抽出
  • 工学系：OpenSees／Code_Aster入力案、単位・境界条件検査、結果説明、再現性確認
  • 現場系：品質・安全・工程遅延・気象作業可否・維持管理・災害初動の判断支援
  • Skillごとに許可ツールと評価セットを持ち、Registryに登録する
  • 理由：Agentを19種類並べると、評価・権限・証跡の管理対象がAgentの数だけ増える。7名体制で保守できる数に抑える

5.2 認可は二重にかける

第1層：MCAH Policy Engine（事前判定）

R0〜R4で判定し、許可されない操作はそもそも呼び出さない。

第2層：MCIP Tool API（最終判定）

RLSで案件権限を確認し、許可されない呼出しを拒否する。

両層とも同じHarness Coreのポリシー定義を読むので、判定がずれない。実効権限は次の積集合とし、モデルの制約も含める。

実効権限 ＝ 利用者 ∩ Agent ∩ Skill ∩ Tool ∩ 案件Policy ∩ データ品質条件 ∩ 機密区分で許可されたモデル

5.3 自作する範囲と既存部品を使う範囲

自作する（差別化の源泉）既存の部品を使う
Policy Engineの判定ロジック（R0〜R4）実行ループ：Pydantic AI または LangGraph（特定モデルに依存しない）
Evidence Verifierモデル接続：LiteLLM
建設業務Skillと評価セットツール接続：MCP公式SDK
各システム用のTool Adapterポリシー記述：OPA／Cedar
承認待ちの状態管理（R2・R3）トレースと評価：Langfuse、promptfoo

承認待ちは数日かかることがあるため、実行状態をPostgreSQLに保存して再開できる設計にする。Temporalは7名体制では運用が重いため採用しない。

5.4 自己改善はR4として扱う

  • 「評価付きの改善」は、改善案をPRとして出す → ゴールデンセットの回帰試験に合格する → 人が承認する、の3つを満たした場合だけ反映する。
  • 無承認の自己改善・再帰的自己改善（RSI）は、MVP後もPolicy Engineで恒久的に拒否する。

5.5 MCAHリポジトリ構造（設計案への追加分）

7. 証跡・運用の標準

証跡（Evidence）の必須項目

  • source_system／document_id／version／locator
  • content_hash／fetched_at／license／classification
  • event_time／location／coordinate_system／sensor_quality
  • model_provider／model_version／prompt_skill_version／tool_version

不合格の回答は返さない。

評価・可観測性（AI Control Center）

  • ゴールデンセット（実際の質問約50問＋期待出典）で回帰試験
  • モデル・プロンプト・Skill変更ごとに実行し結果を記録（promptfoo）
  • Tool Call・コスト・失敗・拒否を全件追跡（Langfuse）
  • Prompt Injection・権限逸脱のレッドチーム試験を定期実施
  • 画像・動画AIは誤検知／見逃し、3Dは位置・寸法精度、予測AIはドリフトと適用範囲外を監視

PostgreSQL 運用

  • 専用本番機、PITR、レプリカ1台以上、システム別スキーマ
  • RLSで案件単位の制御、監査ログは追記専用
  • Agent用ロールは最小権限（読み取り＋台帳＋承認待ち状態のみ）

配備・ガバナンス

  • コンテナ・IaC・GitHub Actions、連邦型ガバナンス v1.0 のGateを共通化
  • Agentごとにサービスプリンシパル、短命トークン
  • モデル・Skill・MCP・依存関係のSBOMをRegistryで台帳化
